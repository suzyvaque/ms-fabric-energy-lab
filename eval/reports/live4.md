# live4: storage format latency (lakehouse vs SQL database vs mirrored Azure SQL vs Eventhouse)

Sample, not production guidance. Synthetic data. Generated by `py eval/live4.py report`. Dedicated capacity F128 (not shared with the evaluation loop), dev workspace `<prefix>-live4-dev`. Frozen snapshot of 6 hub tables taken 2026-11-12T03:39 UTC (989 rows, PII columns dropped). 41 golden questions; truth identical on all engines (lakehouse, sqldb, sqldb_endpoint, eventhouse, mirror). Raw output stays in the gitignored `eval/runs/live4/`.

| Store | Load path | Snapshot -> queryable |

| SQL database | T-SQL batched INSERT (PK per table) | immediate (engine); analytics endpoint replicates to OneLake |

## Findings

- **The store doesn't change agent latency.** Median answer 10.5-10.8 s across the four stores (spread 0.3 s), p95 within ~2 s, and the in-agent query step rounds to 1 s on every store. As in D-038, the time is AI orchestration (planning, NL2SQL/NL2KQL, answer writing); prompt tokens per answer are within 1 % because the instructions and schema are identical.
- **Engines differ by tens of milliseconds, which the agent can't show.** Net of the round trip, the SQL database engine (1 ms) and the Eventhouse (4 ms) answer these small queries fastest; the three SQL analytics endpoints (lakehouse 48 ms, SQL database endpoint 44 ms, mirror 31 ms) add ~30-50 ms of Delta/OneLake overhead. That is <1 % of a ~10 s answer.
- **A SQL database source is queried through its SQL analytics endpoint**, not the database engine (the data agent runs T-SQL on the OneLake replica). So lakehouse, SQL database and mirror agents all hit the same engine type; only the Eventhouse agent uses a different engine (KQL).
- **Accuracy is a wash** (91-94 %, 2-3 flaky questions per agent across 3 reps). The failures are the same questions on every store (the inverter-recall ambiguity from live3, the critical-site/product tie-break). The one store-sensitive case was the multi-hop inverter/High-alert principal, which the KQL agent got 3/3 and the SQL agents 0-1/3.
- **Choose the store for the workload, not for agent speed**: streaming/time series -> Eventhouse; OLTP writes -> SQL database; existing Azure SQL -> mirroring; files/Spark -> lakehouse.

## Setup notes

- **Dedicated capacity.** live4 ran on its own F128 capacity and workspace, so it took no CUs from the evaluation loop on the lab capacity (apart from one read of 989 rows from lh_asset for the snapshot). It is paused after the run.
- **SQL database source type.** The data agent definition schema doesn't list SQL database; `sql_database` works (`data_warehouse` and `mirrored_database` pointing at it fail to connect).
- **Lakehouse timestamps.** The Load Table API writes parquet timestamps as `timestamp_ntz`, which the SQL analytics endpoint hides (the column disappears). The tables are written with UTC `timestamp` instead.
- **Private Azure SQL.** Tenant governance disables public network access and an MCAPS policy requires Entra-only authentication. The server is reached through a private endpoint (DNS zone group required), loaded once by a notebook over a workspace managed private endpoint (Entra token, no password), and mirrored through a VNet data gateway. Through that gateway the SQL connection supports Basic, OAuth2 or service principal only (no workspace identity), so the connection uses OAuth2 and was created in the portal. West US 2 refused new SQL servers, so the server is in West US 3 (only replication crosses regions).
