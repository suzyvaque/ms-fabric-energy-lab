| D-011 | 2026-11 | Experiments use the `lab_` prefix, stay in dev, and are excluded from prod by `infra/deploy.py` (`item_name_exclude_regex`). | Keeps comparison artifacts reproducible in Git without promoting them. | Separate lab workspace (another domain assignment and Git folder). |
| D-012 | 2026-11 | Eventhouse medallion: bronze = raw envelope + `raw:dynamic` (direct ingestion, streaming); silver via **non-transactional update policies** (normalize v1/v2, flag but keep bad rows); dedup via `take_any` MV (lookback 6h); gold MVs over the dedup MV (store **sums + counts**); a stable "Fleet API" of stored functions is the only contract for dashboards, Activator, agents and the API layer. | Raw replay stays possible; silver never blocks bronze; dedup is exact and cheap within the retry window; additive gold aggregates merge correctly; consumers are insulated from table changes. | Eventstream operators (processor CU); transactional update policies (a bad transform drops bronze); `avgif` MVs (NaN for empty groups). |
| D-013 | 2026-11 | KQL source of truth = `infra/kql/eh_fleet/*.kql`, applied through the KQL DB item definition; Fabric's serialized `DatabaseSchema.kql` (committed from Fabric) is what fabric-cicd deploys. | D-014 | 2026-11 | Finance external sources = **open mirroring** (simulated loan-servicing OLTP publishing parquet change files) plus a **cross-domain OneLake shortcut** to the Asset domain's `lh_asset`. | D-015 | 2026-11 | Spark on F2 uses a workspace **custom pool with Small nodes** (`pool_small`), set by script for dev and prod. | F2 = 4 Spark vCores (×3 burst). | D-016 | 2026-11 | One non-schema lakehouse per domain with `bronze_`/`silver_`/`gold_` prefixes. Bronze is **shortcuts** (zero copy) where a governed copy already exists (mirror, other domain). Silver and gold are full rebuilds (idempotent) with a `gold_dq_results` table. `delinquent` = **30+ days past due** at month end, from the start of the unpaid streak; arrears are a separate measure. | Load-to-Table API and broad tool support without schemas; consumers read one lakehouse; shortcuts avoid copy drift; small data volumes make full rebuilds cheap and safe. Cumulative arrears alone flagged 41 % of months (partial-payment residue). | Schema-enabled lakehouse; incremental MERGE (worth it at larger volumes). |
| D-017 | 2026-11 | API layer = **API for GraphQL** over the finance gold SQL endpoint (query-only, PII columns unmapped) + the Eventhouse **Fleet API** stored functions over KQL REST. | D-018 | 2026-11 | Activator (Reflex) items are **script-managed and excluded from Fabric Git commits** (`infra/git_sync.py` selective commit skips `act_*`); recipients come from `.env` (`ALERT_EMAIL`, else `ADMIN_UPN`). | Reflex definitions serialize recipient addresses (tenant accounts), which must not reach this public repo. | D-019 | 2026-11 | Activator rules use the **EventTrigger on a time-axis KQL source** pattern (Skills for Fabric `activator-cli`). | D-020 | 2026-11 | Data agents: one per domain plus a cross-domain `da_contoso_360` (in the Asset workspace, the shared master). | D-037 | 2026-11 | Instructions vs ontology is measured with **two dev-only arms on the ontology agent's exact source** (lh_asset hub, the same 7 tables, the same PII deselection): `lab_da_hub_rich` (everything the ontology encodes plus business definitions, in prose, with 6 pattern few-shots that are not golden questions) and `lab_da_hub_bare` (one line). `da_contoso_360` stays as a different-source reference. | D-038 | 2026-11 | Data agent latency is sized on **AI orchestration, not capacity**: evaluation runs use F32 or larger only to avoid F2 throttling, and capacity is not scaled up to speed agents. F512 was not measured. | Full golden set × 4 agents at F32, F64 and F128: median 12.4–13.5 s and p95 28–36 s with no trend; in-agent SQL/KQL ~1 s and direct engine queries ~0.7 s at every SKU. F2 throttled because streaming, agent and truth queries share CUs. | Scale to F512 for latency (no measured benefit, ~$92/h); run evaluations on F2 (429s on every KQL query). |
| D-039 | 2026-11 | Agent improvement is a **gated feedback loop**, not a prompt rewrite: failures are logged to an Eventhouse (`lab_agent_eval`, every tool call with its data source, tokens, versions, decisions); a Foundry optimizer (gpt-4.1) proposes instruction/few-shot changes from **train** failures only; deterministic guardrails reject golden leakage, PII-rule removal, oversize and few-shots that fail or return no rows; candidates are separate `lab_` agents evaluated **paired** with the head and accepted on **validation** (train gain >= 2 or all remaining, validation not worse, no forbidden-data failure, no category drop > 1); **test** is scored once. Only `lab_` heads advance automatically; real agents need human approval (next phase: prod + CI/CD). | Unguarded optimizers overfit the questions they see and invent definitions and filter values (observed); a fixed three-way split and a paired, gated comparison make accept/reject decisions trustworthy under run-to-run noise of 1-3 questions. Eventhouse makes the loop observable while it runs (Real-Time dashboard, Activator). | Let the optimizer edit agents directly; accept on train accuracy; two-way split reused every round (tunes to the holdout); log to files only. |
| D-040 | 2026-11 | Storage format is chosen **for the workload, not for data agent speed** (live4): lakehouse, SQL database in Fabric, mirrored Azure SQL and Eventhouse holding the same frozen snapshot gave the same agent latency (median 10.5-10.8 s, in-agent query ~1 s) and accuracy (91-94 %). live4 ran on a **dedicated F128 capacity and workspace** (`ce-live4-dev`) so it didn't share CUs with the live2.5 loop. | Data agents query SQL database and mirror sources through their SQL analytics endpoints, so three of four arms hit the same engine. Engine-only, the SQL database engine and Eventhouse were ~30-50 ms faster than the analytics endpoints, under 1 % of an answer. The private Azure SQL needed Entra-only auth (MCAPS policy), a private endpoint + DNS zone group, a managed private endpoint to load it and a VNet data gateway with an OAuth2 connection (no workspace identity through the gateway). | Run live4 on the lab capacity (would skew the live2.5 loop); open mirroring for the mirror arm (kept as fallback); service principal secret for the mirror connection (avoided). |
